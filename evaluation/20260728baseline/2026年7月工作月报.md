## 工作主要内容

### 夏寒柯

1. LMCache 单卡实验框架与 baseline 整理。

   围绕 LMCache 单卡链路，统一整理了原生 vLLM baseline、LMCache SSD-only baseline、LMCache GDS baseline、LMCache + BaM shadow 与 prefer-load 等脚本入口，并同步整理了 evaluation 目录下的 README、结果文档和日志组织方式，形成了可复用的实验框架。

2. vLLM + LMCache + BaM 真实链路调试与收束。

   围绕真实 vLLM 推理流程，继续排查 LMCache connector、storage manager、BaM shadow write、prefer-load、KV fast path 与 direct placement 的调用关系，明确了当前 request_1 写入、request_2 共享前缀读回、GPU worker 搬运与 vLLM 计算推进之间的数据流。

3. GPU worker persistent one-copy 路径稳定性修复。

   针对 cta=4 场景下出现的卡住问题，重点排查了 submit、CQ polling、ready flag、metadata-ready flag、mover CTA 分工、runtime attach 与 finalize 等关键路径，回退并清理了部分过度收束后引入的不稳定逻辑，最终恢复并验证了 cta=4 one-copy 路径的可运行性。

4. BaM KV restore 与 direct placement 性能定位。

   通过日志与性能指标分析，拆解了 BaM 路径中的 submit、poll、read、place、refill 等阶段开销。当前 8k-12k 样本中 BaM 内部 KV restore 可达到百毫秒量级，但端到端 request read 时延仍受 vLLM 计算、调度与同步开销影响，尚未形成稳定压倒性优势。

5. CPU SSD、GDS 与 BaM baseline 对比实验。

   在统一 Qwen2.5-7B-Instruct、LongBench / Tutti-style 数据集和 LMCache 配置下，对 CPU SSD 路径、GDS 路径与 BaM one-copy 路径进行了 smoke 和 baseline 测试，整理了 read_avg、write_avg、avg_request、BaM read_ms、poll_ms 等指标，并形成用于 PPT 展示的主表与补充证据。

6. 冷读与 CPU cache 影响分析。

   针对 LMCache 原生 SSD 路径可能受 CPU page cache 影响的问题，尝试使用 cold read 与 cgroup 方式限制 CPU 缓存，分析传统 CPU-driven SSD 读取路径的真实性能。实验过程中明确了 vLLM 模型加载、KV cache、Python runtime、tokenizer、LMCache metadata 等组件对 CPU 内存的需求边界。

7. GPU-initiated 后续优化方向分析。

   结合 Nsight / NVTX 观测、CPU 调度测试和 CUDA Graph 对比，分析了 GPU-initiated 范式相较传统 GDS 的潜在优势与瓶颈。当前结论是：完整 GPU-side decode loop 改动较大且短期收益不确定，更合理的切入点是 layer-group KV prefetch、IO-compute overlap、CUDA Graph bucket 与多请求 batch 下的调度摊薄。

8. Layer-group prefetch 与多请求流水线思路整理。

   基于当前 BaM KV restore 时间、prefill 计算窗口和 decode layer 结构，整理了跨请求 prefill 隐藏 KV restore、单请求内部 layer-group decode prefetch 的调度思路。将 Qwen2.5-7B 的 28 层按多个 layer group 切分，提出计算 G0 时预取 G1、计算 G1 时预取 G2 的流水线方案，并整理为 PPT 可展示的流程图和讲稿。

9. Tutti 相关数据集下载与整理。

   调研 Tutti 的问题设定与数据使用方式后，下载并整理了 LEval / LooGLE 长上下文数据，构建 Tutti-style combined manifest。当前数据集共 2600 条样本，覆盖多个长上下文任务和长度 bucket，可用于后续复现长上下文 KV cache offloading、prefix reuse 与 SSD KV restore 压力场景。

## 未来工作计划

### 夏寒柯

后续工作将优先围绕 BaM 路径真正能够放大优势的场景继续推进。短期重点不是直接重构完整 GPU-side decode loop，而是在当前已跑通的 BaM one-copy / direct placement 主线基础上，继续实现 layer-group KV prefetch 和多请求 IO-compute overlap，使 KV restore 从单请求 decode 前的串行等待转移到 prefill 或前序 layer group 的计算窗口中。

同时继续完善 Tutti-style 长上下文数据集上的正式实验，补齐 CPU SSD、GDS、BaM one-copy、BaM prefetch 等路径在统一配置下的性能对比，重点观察 read_avg、TTFT、decode throughput、BaM restore time 与端到端 request latency。后续还将继续评估 CUDA Graph bucket、取消 enforce-eager、persistent GPU worker 调度策略以及 GPU-visible placement metadata 对系统性能的影响。
