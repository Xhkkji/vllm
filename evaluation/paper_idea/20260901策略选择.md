# GranuleKV 策略选择与研究方向判断

> 更新时间：2026 年 9 月 1 日  
> 当前阶段：GranuleKV I/O 后端基本完成，开始选择和建立上层策略 baseline。

## 一、核心判断

GranuleKV 最初的出发点是将 Sparse Attention 与 Layer-wise Prefetch 结合：Sparse Attention 决定“读哪些 KV”，Layer-wise Prefetch 决定“什么时候读 KV”，GranuleKV 负责将这些细粒度、离散且并发的访问转换为 GPU-initiated 异步 SSD I/O。

截至 2026 年 9 月，这一问题已经出现多项直接相关成果。SolidAttention、HiSparse 和 AsyncTLS 已经分别覆盖 SSD-backed sparse attention、分层 KV 工作集以及异步稀疏卸载；TARDIS 和 Tutti 则开始解决 GPU-centric SSD KV 服务。因此，以下表述已经不足以单独构成创新点：

- Sparse Attention 与 Layer-wise Prefetch 的简单组合；
- GPU-initiated 异步 SSD I/O 本身；
- 单一请求内的 SSD-aware prefetch；
- 将多个已有策略接到统一接口上的工程集成。

后续研究重点应从“实现一种稀疏预取机制”提升为：

> 面向 SSD 驻留稀疏 KV 的跨请求与请求内联合调度：根据稀疏访问价值、层级使用期限和 SSD 服务代价，动态决定哪个请求的哪些 KV 单元应优先恢复。

GranuleKV 在这一方向中的角色是提供统一的 GPU-initiated、异步、细粒度 I/O 执行底座，而不是重新提出一种 Sparse Attention 算法。

## 二、最新相关成果地图

### 2.1 Sparse KV 选择与稀疏运行时

| 工作 | 时间与状态 | 核心机制 | 与 GranuleKV 的关系 |
| --- | --- | --- | --- |
| Quest | ICML 2024 | Query-aware、block-wise KV page selection | 适合作为首个“读哪些 KV”的训练无关 selector |
| InfLLM | NeurIPS 2024 | 通过 context memory 和 representative vector 选择相关块 | SolidAttention 的动态块选择与其思路接近 |
| LServe | MLSys 2025 | 统一结构化稀疏模式和分层 KV page selection | 主要解决 GPU 内稀疏 attention，不直接解决 SSD I/O |
| ShadowKV | 2024-2025 | 保留低秩 key、卸载 value，并动态恢复稀疏 KV | 可作为 CPU-mediated sparse offload 对照 |
| NOSA/NOSI | 2025-2026 预印本 | 将可训练稀疏模式与 CPU-GPU 卸载约束联合设计 | 说明稀疏策略开始显式考虑传输代价 |

### 2.2 Sparse Attention 与分层预取

| 工作 | 时间与状态 | 核心机制 | 与 GranuleKV 的关系 |
| --- | --- | --- | --- |
| SolidAttention | FAST 2026 | KV block consolidation、动态块稀疏、基于上一 decode iteration 的 speculative prefetch、SSD-aware pipeline | 已覆盖“SSD + sparse + speculative prefetch”，但仍使用 CPU I/O thread 和 DRAM/VRAM buffer |
| AsyncTLS | 2026 预印本 | Block filtering、token selection 和异步 offloading | 与分级稀疏和计算-I/O 重叠相关，但不是 SSD 多请求联合调度 |
| HiSparse | 2026 预印本 | Host 保存完整 KV，GPU 保存固定工作集，执行精确 miss resolution、LRU 和 layer-wise prefetch | 当前最接近“Sparse Attention + Layer-wise Prefetch”的工作，并已合入 SGLang |

HiSparse 是当前最需要重视的直接相关工作。它支持 DSA、NSA 和 Quest 等不同 selector，并将完整 KV 保留在 host memory，只把被选中的 KV 放入有限 GPU cache。对于能够跨层共享选择结果的模型，它进一步使用精确的 layer-wise prefetch 隐藏部分 host-to-device miss 开销。

HiSparse 基本证明了“稀疏选择 + 有界 GPU 工作集 + layer-wise prefetch”的可行性，但其主要容量层是 host memory，剩余性能瓶颈仍是 host-to-device I/O。GranuleKV 的可区分空间是将容量层进一步扩展到 SSD，并研究 SSD 队列竞争、细粒度请求代价和多请求调度。

### 2.3 GPU-centric SSD KV 服务

| 工作 | 时间与状态 | 核心机制 | 与 GranuleKV 的关系 |
| --- | --- | --- | --- |
| TARDIS | APSys 2025 | GPU-centric KV cache service、layer-wise asynchronous operation | 与 GranuleKV 的异步底座定位明显重叠 |
| Tutti | 2026 预印本 | GPU-native KV object、GPU io_uring、SSD-HBM object I/O、slack-aware I/O scheduling | 是 GranuleKV 底层执行路径最强的相关工作 |

TARDIS 与 Tutti 的作者和问题定义高度重合，可以暂时视为同一技术路线的逐步扩展。它们说明“绕开 CPU 高频 I/O 发起、由 GPU 驱动 SSD-HBM 传输”已经不能作为 GranuleKV 唯一的论文贡献。

GranuleKV 后续需要把底层能力转化为新的策略问题：如何让 Sparse Attention 的动态选择结果、Layer-wise Prefetch 的使用期限和多请求公平性共同决定 GPU-initiated I/O 的提交顺序、聚合粒度和资源预算。

Tutti 已公开完整工程仓库，而不只是论文中的原型描述。当前公开版本为 `v0.1.1`，提供稳定的 `StorageRuntime` API，接口包括 `open/open_batch/register/submit/wait`；底层包含 `snvme` 内核模块、`tutti_daemon`、GPU io_uring、单盘与多盘 striped data path、测试和 vLLM connector。仓库还提供 `layerwise_kv_overlap` 参考负载，用于验证逐层 KV 的 read/compute/write overlap。因此，Tutti 应作为 GranuleKV 最重要的公开底层 baseline，而不能只作为定性相关工作。

### 2.4 请求级存储感知调度

Bidaw（FAST 2026）面向交互式 LLM serving，使用 SSD 容量层和 host DRAM 性能层，并将请求分为 KV 已在 DRAM 的 ready queue 和 KV 尚在 SSD 的 preparing queue。其 Disk-HRRN 使用以下响应比调整请求顺序：

```text
response_ratio = 1 + waiting_time / KV_size
```

Bidaw 很适合作为请求级 I/O-aware scheduling baseline，但它通常以“请求需要恢复完整 KV”为基本服务对象。Sparse Attention 与 Layer-wise Prefetch 引入后，一个请求不需要等待全部 KV 恢复，只要最早即将使用的层窗口和稀疏块就绪，就可以继续执行。因此，Bidaw 的 `KV_size` 不再是准确的服务代价。

| TARDIS | 未发现官方源码 | [DOI:10.1145/3725783.3764393](https://doi.org/10.1145/3725783.3764393) | APSys 论文公开，但未找到作者发布的 GPU-centric KV service 仓库，不适合要求代码级完全复现 |

| Bidaw | 未发现官方源码 | [FAST 2026 论文页](https://www.usenix.org/conference/fast26/presentation/hu-shipeng) | USENIX 页面提供论文、演讲和幻灯片，但未发现源码链接；Disk-HRRN 和双队列策略相对清晰，适合依据论文自行实现 baseline |

从代码可获得性出发，可以进一步分为三组：

```text
可以直接运行或移植：
Quest、InfLLM、LServe、ShadowKV、NOSA、HiSparse/SGLang、Tutti

可以根据论文复现核心策略，但不能宣称复现官方系统：
SolidAttention、AsyncTLS、Bidaw

更适合作为机制和论文定位对照：
TARDIS
```

这会影响后续实验表述：对于 Quest、HiSparse 和 Tutti，可以使用“基于官方实现复现”；对于 SolidAttention 和 Bidaw，应使用“SolidAttention-style speculative prefetch”和“Bidaw-style Disk-HRRN”；对于 TARDIS，在没有获得官方 artifact 前，不应声称完成了系统级复现。

### 2.6 源码情况对复现顺序的影响

结合研究相关性和代码可用性，推荐顺序调整为：

1. **Quest 官方实现**：先验证 selector 精度和 block mapping，再接入 GranuleKV；
2. **HiSparse/SGLang 上游实现**：建立 host-to-device 分层稀疏恢复 baseline，并观察其 layer-wise prefetch；
3. **Tutti 官方实现**：独立建立 GPU-centric SSD 底层 baseline，先复现单盘 microbenchmark 和 `layerwise_kv_overlap`，再决定是否运行其 vLLM connector；
4. **ShadowKV 官方实现**：在硬件和模型条件允许时建立 CPU-mediated sparse offload baseline；
5. **SolidAttention-style 策略复现**：只实现 speculative prefetch、miss correction 和统计，不复刻未公开的全系统；
6. **Bidaw-style 策略复现**：依据论文实现双队列与 Disk-HRRN，并清楚标注为 reimplementation；
7. **GranuleKV 联合调度**：固定已经验证的 selector 和 I/O backend，再加入 request、layer-window、sparse block 联合优先级。

虽然 LServe、InfLLM 和 NOSA 均有公开代码，但它们分别涉及独立 serving runtime、算法型 context memory 和模型训练，第一阶段不应仅因为“有源码”就排在 Quest 与 HiSparse 之前。

Tutti 的公开不意味着应立即把 GranuleKV 替换为 Tutti。两者应先以相同 SSD、GPU、请求粒度和数据规模做底层对照。Tutti 的公开运行环境要求裸机、IOMMU passthrough、指定 Linux kernel lineage、`snvme` 模块和 daemon，且其公开高带宽结果包含四块 NVMe striping；这些条件需要与当前 GranuleKV 单机环境对齐后，才能公平比较。

## 三、复现优先级

### 3.1 第一优先级：HiSparse

首先在其原生 SGLang 环境中运行已有实现，确认以下行为：

- 不同 sparse selector 的选择结果；
- GPU 固定容量工作集；
- block hit、miss 和 LRU replacement；
- 跨层共享选择下的 layer-wise prefetch；
- no-I/O oracle 与真实 host-to-device I/O 的差距。

随后不直接移植整套 SGLang runtime，只将其策略语义映射到 GranuleKV：

```text
sparse selection        -> block_mapping
layer-wise prefetch     -> stage_plan() / submit_request()
miss correction         -> 补充 request
request completion      -> query_request() / complete_request()
GPU working-set policy  -> vLLM 调度侧状态
```

这样可以固定 GranuleKV 后端，比较 host-mediated HiSparse 和 SSD-direct GranuleKV 的数据路径，同时避免把两个推理框架的实现差异混入结论。

### 3.2 第一优先级：Quest selector

第一阶段建议使用 training-free、block-wise 的 Quest，而不是立刻更换为原生 DSA 或 NSA 模型。这样可以保持模型、数据集、KV 格式和 attention 语义基本不变，将实验变量集中在 selector、预取和 I/O 调度上。

Quest 需要先在 HBM 内验证选择质量，再接入 GranuleKV：

1. Full Attention，作为精度和输出基准；
2. Quest selector，KV 仍全部位于 HBM；
3. Quest selector，选中块由同步 SSD I/O 恢复；
4. Quest selector，选中块由 layer-wise async prefetch 恢复。

只有 selector recall、任务精度和 attention 输出误差满足要求后，才能把性能提升归因于 I/O 和调度，而不是错误丢弃 KV。

### 3.3 第二优先级：SolidAttention speculative prefetch

不建议完整复刻 SolidAttention 的 CUDA/SYCL runtime、K/V interleaved kernel 和全部存储布局。优先复现其策略机制：

- init block、local block 和 dynamically selected block 分类；
- 上一 decode iteration 的选择历史；
- speculative prefetch；
- 正式选择完成后的 miss correction；
- speculative hit、miss、无效预取和 correction read 统计。

这部分可以与 HiSparse 的精确 layer-wise prefetch 形成对照：HiSparse 利用跨层选择共享，SolidAttention 利用相邻 decode iteration 的选择相似性。

### 3.4 第二优先级：Bidaw Disk-HRRN

先复现 ready/preparing queue 和 Disk-HRRN，作为跨请求 baseline。第一阶段不需要复刻 Bidaw 的完整 host cache eviction、ghost cache、回答长度预测和 intermediate tensor caching。

Bidaw baseline 的价值是建立以下对照：

```text
FCFS
Bidaw-style request-level scheduling
GranuleKV layer-wise scheduling
GranuleKV sparse + layer-wise scheduling
GranuleKV 跨请求与请求内联合调度
```

### 3.5 暂不建议完整复现的工作

- TARDIS：未发现官方源码，与 GranuleKV 位于同一底层问题域，优先用于机制和论文定位对照；
- Tutti：已有完整官方源码，应复现底层 microbenchmark 和 layer-wise overlap，但不必在第一阶段复刻其所有多盘、跨 GPU 厂商和完整 vLLM serving 实验；
- SolidAttention 全系统：实现规模较大，第一阶段只复现 selector 和 speculative prefetch；
- Bidaw 全系统：host cache 和 intermediate tensor 不属于当前核心问题；
- NOSA/NOSI：涉及训练和模型修改，适合作为后续扩展，不适合作为首个 baseline。

## 四、最小可比较实验矩阵

固定模型、数据集、上下文、KV block size、SSD 数据、HBM 容量和 GranuleKV 后端，只改变上层策略：

| 编号 | Sparse selector | I/O 方式 | 请求调度 | 目的 |
| --- | --- | --- | --- | --- |
| A | 无，完整 KV | 同步 full restore | FCFS | Dense baseline |
| B | Quest | 同步 on-demand | FCFS | 观察只有“读哪些 KV”的收益 |
| C | Quest | Layer-wise async prefetch | FCFS | 观察“什么时候读”的收益 |
| D | Quest | SolidAttention-style speculative prefetch | FCFS | 观察推测预取和 correction 代价 |
| E | Quest | Layer-wise async prefetch | Bidaw Disk-HRRN | 请求级 I/O-aware baseline |
| F | Quest | Layer/block async prefetch | 联合调度 | 最终方案 |

实验应统一 prefill 一个持久化前缀，将完整历史 KV 写入 SSD，再执行多 token decode。每轮只恢复当前 attention 真正需要的历史 KV；新生成 KV 可暂时驻留 HBM，从而将实验重点保持在 SSD 到 GPU 的恢复路径上。

## 五、指标体系

### 5.1 选择质量

- selector recall；
- attention output error；
- LongBench、RULER 或 Needle-in-a-Haystack 等任务精度；
- 不同 KV budget 下的质量变化。

### 5.2 预取质量

- prefetch precision 和 recall；
- speculative hit rate；
- wasted prefetched bytes；
- correction-read bytes 和 correction latency；
- 首个 layer window 就绪时间与完整恢复时间。

### 5.3 I/O 与执行

- SSD 有效带宽；
- descriptor 数量和平均 descriptor 大小；
- 请求聚合前后的 I/O 数量；
- GPU barrier wait 和 attention stall；
- I/O 与 compute 的重叠比例；
- HBM working-set 峰值。

### 5.4 Serving 指标

- TTFT、TPOT、端到端延迟和吞吐；
- P50、P95 和 P99；
- 请求等待时间与 starvation；
- 不同上下文长度和请求并发度下的公平性。

## 六、与 Bidaw 结合后的创新方向

### 6.1 从请求级调度升级为层次化调度

Bidaw 的调度对象是完整请求。Sparse Attention 与 Layer-wise Prefetch 下，更合理的调度对象是：

```text
request × decode step × layer window × sparse block set
```

不同 KV 单元具有不同的使用期限、选择置信度、I/O 成本和 stall reduction。调度器不应只决定“哪个请求先恢复”，还应决定“该请求的哪些层和哪些块先恢复”。

### 6.2 重新定义服务代价

Bidaw 使用完整 `KV_size` 近似 SSD 服务时间。稀疏场景下应改为：

```text
expected useful bytes
earliest-admissible window bytes
predicted correction bytes
estimated SSD service time
```

其中，`earliest-admissible window` 表示能够让请求尽早恢复执行的最小 KV 集合。一个请求即使只恢复了部分 KV，也可能已经具备执行当前层的条件。

### 6.3 联合优先级模型

调度优先级至少应综合：

- 请求等待时间与公平性；
- 距离 KV 实际使用时刻的 layer deadline；
- sparse selector 的选择置信度；
- expected useful bytes；
- speculative miss 和 correction 风险；
- SSD 队列状态与预计服务时间；
- 完成该单元能够减少的 GPU stall。

可以将核心优化目标表述为：

> 在模型精度、HBM 容量和请求公平性约束下，最大化单位 SSD I/O 所避免的 GPU 停顿。

这比简单组合 Bidaw 和 Layer-wise Prefetch 更具有学术意义，因为它改变了调度对象、服务代价模型和优化目标。

### 6.4 双向策略与后端感知

CPU/vLLM 调度侧负责：

- 请求 admission 和公平性；
- sparse block set；
- layer deadline；
- prefetch budget；
- 请求优先级和逻辑粒度。

GPU/GranuleKV I/O 侧反馈：

- descriptor pool 占用；
- SSD queue depth；
- physical ready 和 completion；
- 实际服务时间与有效带宽；
- 请求聚合后的物理 I/O 规模。

调度侧可以根据这些反馈动态调整 token、block、layer-window 的请求组织粒度。这一机制不是让 GranuleKV理解某一种 Sparse Attention，而是让统一 I/O 后端能够执行并反馈多种策略产生的动态访问计划。

## 七、与已有工作的差异边界

### 相对 SolidAttention

SolidAttention 重点是内存受限 PC 上的单请求或低并发 SSD sparse attention pipeline，使用历史选择进行 speculative prefetch。GranuleKV 应重点研究多请求竞争、GPU-initiated direct path 和统一请求调度，而不是再实现一种类似的 block selector。

### 相对 HiSparse

HiSparse 重点是 host memory 容量层、固定 GPU 工作集和精确 layer-wise prefetch。GranuleKV 的差异应放在 SSD 容量层、SSD 队列代价、细粒度 GPU-initiated I/O 以及跨请求调度上。

### 相对 TARDIS/Tutti

TARDIS/Tutti 已经覆盖 GPU-centric SSD KV service。GranuleKV 不能只强调绕开 CPU，而应强调 sparse usefulness、layer deadline 和 request fairness 如何共同控制 GPU-initiated I/O。

### 相对 Bidaw

Bidaw 是请求级、完整 KV 恢复和 host cache 感知调度。GranuleKV 应将请求拆为可独立产生执行价值的层窗口和稀疏块，并研究部分就绪条件下的调度收益。

## 八、建议形成的最终论文主线

```text
Sparse Attention
    决定哪些 KV 有用

Layer-wise Prefetch
    决定这些 KV 何时必须就绪

Bidaw-style Scheduling
    提供跨请求等待与公平性基线

GranuleKV
    执行 GPU-initiated、异步、细粒度 SSD I/O

联合调度器
    在 request、layer-window 和 sparse block 三个层次上
    联合优化有效 I/O、GPU stall、尾延迟与公平性
```

适合当前阶段的总论断是：

> GranuleKV 以 GPU-initiated 细粒度 I/O 为执行基础，将 Sparse Attention 产生的动态访问价值、Layer-wise Prefetch 的时间期限和 Bidaw 式跨请求公平性统一到同一个层次化调度模型中。
