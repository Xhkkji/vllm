## 1. 研究问题与目标

### 1.1 问题背景

在线多轮对话和长上下文推理会持续产生大量 KV Cache。GPU HBM 容量不足时，
系统需要在 GPU、主机内存和 SSD 之间保存、释放和恢复 KV。SSD 扩大了可缓存
容量，但也引入了两个相互关联的问题：

1. **数据路径问题**：传统 `SSD -> CPU -> GPU` 路径存在 CPU staging、内存拷贝
   和同步开销；SSD 读取还会直接进入 TTFT 或恢复后的首个 decode step 的关键路径。
2. **调度问题**：如果 swap 代价太高，scheduler 会倾向于让已运行请求继续执行，
   后续请求长期停留在 waiting queue；如果频繁抢占，又会产生重复写回和恢复，
   放大 SSD I/O、GPU bubble 和尾延迟。

因此，本项目的目标不只是提高一次 SSD 读写的带宽，而是让 vLLM scheduler
感知 KV block 的位置、脏净状态和 I/O 代价，并与 BaM 的 SSD-GPU direct I/O
协同，减少不必要的数据移动和前台等待。

### 1.2 核心研究问题

当前论文需要回答以下问题：

1. 在真实多轮到达和 GPU KV 容量压力下，vLLM 的 waiting、preemption 和 KV
   换入换出如何共同影响 TTFT、TPOT 和尾延迟？
2. SSD-GPU direct I/O 相比 `SSD -> CPU -> GPU` 能消除哪些开销，剩余瓶颈为何
   仍然可能来自 scheduler？
3. scheduler 是否可以依据下一轮工作集保留仍会使用的 GPU KV block，并对已有
   SSD 副本的 clean block 免写释放，从而降低 write-read amplification？
4. 如何同时实现关键路径 read 优先、非关键 write 延后，又避免等待请求饥饿？
5. request/sequence 级调度是否已经足够；什么情况下需要继续下沉到 layer-group
   或 attention-inner microtask 粒度？

### 1.3 当前待验证假设

- **H1：双副本复用降低写放大。** 对已有有效 SSD 副本的 clean prefix，释放 GPU
  block 时无需再次写盘，只写自回归生成后发生变化的 dirty suffix。
- **H2：工作集感知降低读放大。** 如果下一轮仍会调度某些请求，则让其 KV block
  继续驻留 GPU，可减少由 sequence 级抢占造成的重复 SSD restore。
- **H3：I/O 感知调度改善尾延迟。** 将 KV 已就绪请求与需要 SSD 读取的请求分开
  管理，并在考虑等待时间的同时控制读量，可降低 queueing time 和 TTFT 尾延迟。
- **H4：read 优先、write 延后改善关键路径。** restore read 直接决定请求何时恢复
  计算，而 clean/dirty KV 的持久化通常具有更大松弛时间，应避免后台 write 阻塞 read。

## 2. 当前系统进展

### 2.1 当前端到端链路

```text
vLLM request lifecycle
        |
        v
AsyncKVScheduler
  - 选择运行、等待和被抢占的 sequence group
  - 创建 block reserve 事务
        |
        v
Engine / Worker
  - 提交异步 read 或 write
        |
        v
常驻 MDS poll runtime
  - BaM SSD <-> GPU direct I/O
  - 更新 completion/status
        |
        v
vLLM step boundary poll
  - DONE: commit block table 和 sequence 状态
  - ERROR: abort 并回收预留资源
```

当前没有额外引入独立的 engine polling thread。常驻 MDS 负责底层 I/O 推进，
vLLM 在下一次 engine step 的数据依赖边界读取 completion，并执行 `commit/abort`。

### 2.2 已实现机制

- 新增 `AsyncKVScheduler`，通过参数选择；原生 vLLM Scheduler 保持可用且行为不变。
- 打通 MDS 异步 read/write 与常驻 poll 链路。
- 实现 block 级 `reserve/commit/abort`，正式 block table 只在 I/O 成功后切换。
- 使用 chunked prefill 提供更细的 engine step 和 I/O-compute overlap 窗口。
- 建立 GPU/SSD 双副本目录，允许 read 后同时保留 SSD 副本身份。
- 对 GPU 与 SSD 内容一致的 clean prefix 执行无写盘复用。
- 只为发生变化的 dirty suffix 建立 write mapping。
- 当整条 KV 都是 clean 时，允许提交空 write mapping 并直接完成状态迁移。
- 关键 restore read 优先于排队中的后台 write。
- 已加入 submit、device completion、engine observe、commit 等时间线分解。

### 2.3 最新初步结果

以下结果只用于确认双副本与 dirty-suffix 路径已经生效，属于 smoke 结果，
还不能作为最终性能结论：

| 指标 | 双副本驻留前 | 双副本驻留后 | 变化 |
| --- | ---: | ---: | ---: |
| Write requests | 36 | 36 | 0% |
| Read requests | 36 | 36 | 0% |
| SSD write blocks | 4680 | 4166 | -11.0% |
| SSD read blocks | 4680 | 4680 | 0% |
| 累计 write I/O | 2010.3 ms | 1905.9 ms | -5.2% |
| E2E | 103.265 s | 103.394 s | 基本不变 |

这组数据说明：

1. clean block 免写和 dirty suffix 写回已经减少实际写盘量。
2. request 级 preemption 次数没有改变，因此 36 次 read 仍然存在。
3. 仅优化 block 写回不足以改善端到端性能，当前主要缺口已经转向 admission、
   victim selection 和下一轮 GPU 工作集保留策略。

## 3. 相关工作

### 3.1 vLLM 与 LMCache

vLLM 使用 PagedAttention 和 block table 管理 GPU KV Cache。原生 V0 scheduler
在 GPU block 不足时，可以根据配置和 sequence group 形态选择 recompute 或
swap；其 swap tier 原生语义主要是 GPU 与 CPU block 间迁移，而不是直接把 SSD
作为 scheduler 的 block tier。

LMCache 在 vLLM 外增加可复用 KV 存储。标准 SSD backend 的典型读取路径为：

```text
SSD -> CPU buffer -> GPU KV Cache
```

LMCache 可以保存和恢复跨请求前缀，但其 chunk/object 生命周期与 vLLM 原生
block scheduler 并非天然统一。当前项目需要解决的核心正是：让 scheduler 所见的
PagedAttention block 身份、GPU/SSD residency 和 BaM direct I/O 成为同一套状态。

### 3.2 CachedAttention

CachedAttention 面向多轮对话的 session KV 复用，采用分层缓存路径：

```text
HBM -> DRAM -> SSD
SSD -> DRAM -> HBM
```

主要机制包括：

- 按 session 保存多轮上下文 KV，避免每轮重新计算全部历史。
- 使用 layer-wise CUDA write stream、HBM write buffer 和独立 DRAM-to-SSD 线程，
  将保存操作尽可能移出计算关键路径。
- 使用 lookahead scheduling window 观察后续请求，提前进行 KV 准备。
- 使用 session 级 eviction 管理多层缓存容量。

与本项目的关系：CachedAttention 已经证明“驻留、预取和调度联合设计”是多轮 KV
缓存的重要方向，但其数据路径经过 DRAM，管理粒度更偏 session。本项目关注
PagedAttention block 与 SSD-GPU direct I/O 的结合，并进一步区分 clean/dirty block。

### 3.3 SolidAttention

SolidAttention 面向 SSD 支撑的长上下文 sparse attention，其基本数据路径为：

```text
VRAM -> DRAM -> SSD
SSD -> DRAM -> VRAM
```

它不只在请求边界换入整条 KV，而是把 attention 执行表示成包含 KV I/O、buffer
依赖和 attention compute 的 DAG，再拆为 attention-inner microtasks：

- 根据 sparse attention 实际需要选择 KV chunks。
- 将 load、compute、store 建模为细粒度依赖任务。
- 尽量把 store 放到关键路径之外。
- 通过 DAG 调度重叠 KV I/O 与 attention 计算。

SolidAttention 比当前 `AsyncKVScheduler` 更深入。当前路径仍要求被调度 sequence
所需的完整 KV 在进入模型执行前 ready；SolidAttention 则能在 attention 内部边读、
边算、边推进。项目可以先从 request/block 级 I/O-aware scheduling 做起，再根据
实验决定是否下沉到 layer-group 和 attention-inner 粒度。

### 3.4 TARDIS

TARDIS 采用 GPU-centric KV Cache service，核心路径是：

```text
SSD <-> GPU HBM direct
```

其关键机制包括 GeminiFS/GStore、GPU-side scheduler、CUDA Graph、dirty bitmap
和异步持久化。对当前项目最直接的启发是：

- KV Cache 应采用专用对象和状态语义，而不是长期套用通用 tensor I/O。
- dirty bitmap/dirty state 决定是否需要持久化；已有一致 SSD 副本的 clean 数据
  不应重复写盘。
- 高频 I/O completion 推进适合放在 GPU-visible 或常驻 runtime 中，CPU 负责较粗
  粒度的请求策略和元数据准备。

当前双副本目录和 dirty-suffix write 与这一原则一致，但控制面仍由 vLLM CPU
scheduler 驱动，不等同于复现 TARDIS 的完整 GPU-side scheduler。

### 3.5 Tutti

Tutti 研究 SSD-backed KV Cache 的 GPU-centric 数据路径与 I/O 调度，采用：

```text
SSD <-> GPU HBM P2P DMA
CPU prepares metadata, GPU executes I/O
```

主要机制包括：

- GPU io_uring / GPU-resident queue，减少 CPU 参与关键 I/O 控制路径。
- layer-wise `retrieve_layer` / `store_layer`，为 I/O-compute overlap 提供粒度。
- read priority：读取位于请求恢复关键路径，优先于可延后的 write。
- deferred write：根据 layer slack 安排保存，避免 read/write 无约束竞争同一 SSD。
- write 完成后才发布 replica metadata，保证副本状态与持久化顺序正确。
- 通过 vLLM KVConnector 集成，保留 block-granular KV 管理。

Tutti 的主要 baseline 包括：

- 原生 vLLM HBM。
- LMCache-DRAM-LW。
- LMCache-SSD。
- LMCache-GDS。
- DRAM without layer-wise overlap，用于拆分流水化收益。

其主要实验环境和 workload 为：

| 维度 | Tutti 设置 |
| --- | --- |
| 模型 | 单 GPU Llama3-8B；超长上下文使用 GLM-4-9B-Chat-1M、TP=2 |
| GPU | 2 x H100 80GB |
| 主机内存 | 512GB，实验中每 GPU 配置 256GB pinned DRAM |
| SSD | 4 x Solidigm D7-PS1010 7.68TB，每 GPU 约 14TB SSD 容量 |
| 软件 | vLLM 0.12.0/0.17.0，LMCache 0.4.2 |
| 数据集 | LEval 20 个任务，约 3K-200K tokens；LooGLE 4 个超长上下文任务 |
| 到达过程 | 数据集无原生时间戳，使用 Poisson arrivals |
| 指标 | 平均 TTFT、ITL、命中率、带宽、GPU bubble、成本、RPS 和 1 秒 TTFT SLO |

论文设置中的命中率分层为：LEval 的 HBM/DRAM/SSD 命中率约为
`8%/53%/84%`，LooGLE 约为 `4%/24%/86%`。这些设置适合放大长上下文 SSD
restore 压力，但不代表真实交互式多轮请求的到达规律。

与本项目的关系：BaM/MDS 解决的是与 Tutti 相近的 direct I/O 数据路径问题；
read priority、deferred write 和完成后发布副本也可以直接借鉴。当前不需要立即复刻
GPU io_uring 和完整 GPU-native object store，应先验证 block 级调度能否消除
preemption 导致的重复 write/read。

### 3.6 Bidaw

Bidaw（FAST'26）面向真实 interactive multi-turn LLM serving，使用 GPU、主机
DRAM performance layer 和 SSD capacity layer。它的重点不是 SSD-GPU direct I/O，
而是让请求调度和缓存淘汰同时感知 I/O 成本。

#### I/O-aware scheduling

Bidaw 将请求分为两类：

- **Ready queue**：请求所需 KV 已在 performance layer，可直接尝试进入 GPU。
- **Preparing queue**：请求需要先从 SSD 读取 KV。

Ready queue 基本使用 FCFS；从 preparing queue 晋升后仍保留原始 arrival time，
避免因准备过程重新排队。若队首请求无法装入 GPU，scheduler 可以跳过它，先调度
后续能够装入的请求，减少 head-of-line blocking。

Preparing queue 使用 disk-HRRN：

```text
priority = 1 + waiting_time / KV_size
```

较小的 KV read 更容易快速完成，但随着等待时间增加，大请求优先级也会持续上升，
因此能够兼顾吞吐和防饥饿。

#### Eviction 与存储策略

- 使用上一轮 model answer length 预测加权 reuse distance 的下界。
- 真实 trace 上 answer length 与后续复用距离的 Spearman correlation 为 0.94-0.98。
- 使用后台 Belady-style ghost cache 估计不同 KV 的潜在命中收益。
- 淘汰预测 hit potential 最低的 KV，并与 FIFO、LRU、LFU、queue-enhanced policy
  和 Belady upper bound 比较。
- 支持 storage-efficient tensor caching，不要求所有场景都固定保存完整 KV。
- GPU 侧混用 256-token big blocks 与 16-token small blocks，兼顾管理开销和碎片。

Bidaw 的实验设置为：

| 维度 | Bidaw 设置 |
| --- | --- |
| GPU | 1 x A800 80GB |
| 主机内存 | 200GB |
| SSD | 4 x SATA SSD RAID-5，总带宽约 1.5GB/s |
| 总线 | PCIe 4.0 |
| 模型 | OPT-6.7B/13B/30B，Qwen-7B/14B |
| Baseline | vLLM recompute、CachedAttention、FlashGen、all-KV-in-host-memory ideal |
| 主数据集 | 超过 100 万轮的真实 interactive conversation trace |
| 次数据集 | ShareGPT，缺少时间戳，使用 Poisson arrivals |
| 指标 | 平均 E2E、users/min、queueing、host miss、P90/P95/P99、调度开销 |

公开真实 trace 包含：

```text
user_id
timestamp_seconds
query_length
response_length
round_index
```

其平均 query 为 36 tokens，平均 response 为 45 tokens；会话轮数的
平均值/中位数/P90 约为 `22/18/45`，论文另报告平均 22.4 轮。该 trace 只提供
长度而不提供文本，适合使用确定性 token synthesis 复现到达、轮次和 KV 容量压力。

论文报告最高 3.58x latency 降低和 1.83x throughput 提升；其中 I/O-aware
scheduling 单独最多带来 1.58x latency 改善，平均 queueing time 从 5.76s 降到
2.45s。当前只能把这些数字作为论文背景，不能与本项目硬件上的绝对结果直接比较。

还需注意：Bidaw artifact 使用较旧的 vLLM 0.1.7；CachedAttention 和 FlashGen
由于未开源而由作者重新实现。因此，本项目后续应复现其**策略思想**，不应声称
已经获得完全相同的 baseline 实现。

## 4. 相关工作横向对比

| 系统 | 主要问题 | 数据路径 | 主要粒度 | 调度位置 | 可直接借鉴点 |
| --- | --- | --- | --- | --- | --- |
| vLLM | GPU KV 分配与连续批处理 | HBM；V0 swap 到 CPU | block/sequence | CPU scheduler | PagedAttention block identity、admission/preemption |
| LMCache | 跨请求 KV 复用 | SSD -> CPU -> GPU；也支持 GDS backend | chunk/object | connector/storage | 标准 SSD、DRAM、GDS baseline |
| CachedAttention | 多轮 session KV 复用 | HBM <-> DRAM <-> SSD | session/layer | CPU lookahead | 驻留、预取、后台写回 |
| SolidAttention | SSD-backed sparse attention | SSD <-> DRAM <-> VRAM | attention microtask | DAG scheduler | attention-inner I/O-compute overlap |
| TARDIS | GPU-centric KV service | SSD <-> GPU direct | KV object/block | GPU-side | dirty state、异步持久化、GPU completion |
| Tutti | 高效 direct SSD KV I/O | SSD <-> GPU P2P DMA | block/layer | CPU metadata + GPU I/O | read priority、deferred write、完成后发布副本 |
| Bidaw | 真实多轮 I/O-aware serving | SSD <-> DRAM <-> GPU | request/session | CPU scheduler | ready/preparing queue、disk-HRRN、防饥饿 eviction |
| 本项目 | direct I/O 与 vLLM 调度协同 | BaM SSD <-> GPU direct | block，后续可到 layer-group | AsyncKVScheduler + MDS | 双副本、dirty suffix、工作集和 I/O 联合调度 |

最重要的判断是：

> **Bidaw 回答“请求和缓存应该怎样调度”，Tutti 回答“SSD KV 应该怎样高效搬运”。**

二者不是互斥路线。当前项目正好位于二者交叉处：

```text
BaM/MDS direct I/O  -> Tutti-like data-path question
AsyncKVScheduler    -> Bidaw-like scheduling question
```

## 5. 本工作的研究定位

### 5.1 不应单独作为创新点的内容

以下机制属于已有缓存系统的常见原则，不能单独作为论文创新：

- 让下一轮仍会使用的 KV 留在 GPU。
- 已有 SSD 副本的 clean block 不重复写盘。
- 简单地把同步接口改成异步接口。
- 单纯提高 SSD-GPU 读写带宽。

它们应作为系统正确性和后续调度的必要基础。

### 5.2 更有价值的组合定位

建议将论文主线表述为：

> 面向 vLLM 在线推理，构建与 PagedAttention 对齐的 GPU/SSD 双驻留目录，
> 将 scheduler 可见的下一轮工作集与 BaM SSD-GPU direct I/O 联合起来，
> 通过关键 read 优先、dirty write 延后和 I/O-aware admission/victim policy，
> 降低 preemption 引起的 write-read amplification、请求饥饿和尾延迟。

关键组合为：

```text
vLLM scheduler working set
+ PagedAttention block identity
+ GPU/SSD dual residency
+ BaM direct I/O
+ read-priority deferred write
+ I/O-aware admission and victim selection
```

真正需要实验支撑的贡献不是“存在双副本”，而是 scheduler 如何使用副本状态，
在吞吐、公平性、SSD 流量和尾延迟之间做出比原生策略更好的选择。

## 6. 固定 Baseline

### 6.1 系统级 Baseline

| ID | Baseline | 作用 |
| --- | --- | --- |
| B0 | vLLM HBM/Recompute | 不使用外部 KV Cache 的基础对照 |
| B1 | LMCache DRAM-LW | 强 DRAM 性能上界，拆分 SSD 与框架开销 |
| B2 | LMCache SSD | 标准 `SSD -> CPU -> GPU` 路径 |
| B3 | LMCache GDS | LMCache 的 GDS SSD 路径 |
| B4 | BaM MDS Async + FCFS | 当前 direct-I/O 数据路径 baseline |
| B5 | BaM MDS + Bidaw-style disk-HRRN | 请求级 I/O-aware scheduling baseline |
| B6 | BaM MDS + proposed policy | 双副本、工作集、read/write 联合调度的最终系统 |

B5 必须命名为 **Bidaw-style disk-HRRN**，不能写成完整 Bidaw reproduction，原因是
当前系统没有 Bidaw 的 DRAM performance layer、answer-length reuse predictor 和
Belady-style ghost cache，底层数据路径也不同。

### 6.2 内部消融顺序

```text
MDS Sync
  -> MDS Async
  -> + GPU/SSD dual residency
  -> + clean-prefix reuse and dirty-suffix write
  -> + read-priority deferred write
  -> + I/O-aware admission and victim selection
```

每一级只增加一个明确机制，分别回答：异步化、双副本、减写、读写调度和请求调度
各自带来多少收益。

## 7. 固定数据集与 Workload

### 7.1 主 workload：Bidaw 真实多轮 trace

使用 `Interactive-conversation-workload` 作为主要在线多轮实验：

- 保留真实 `user_id`、`timestamp_seconds`、`round_index` 和会话顺序。
- 按 trace 的 `query_length`、`response_length` 生成确定性 token 序列。
- 同一用户的后续轮次必须包含此前对话历史，以形成真实 KV 增长和复用关系。
- 不随机打乱同一 session 内轮次；只按原始到达时间合并不同用户请求。
- 同时报告原始时间缩放因子，避免不同实验使用了不同 arrival compression。

该 workload 用于支撑“真实多轮到达、等待、公平性和尾延迟”结论。

### 7.2 公共多轮 workload：ShareGPT

ShareGPT 用于补充可公开复现的多轮会话：

- 保留 conversation hierarchy 和每轮历史。
- session 到达使用 Poisson process。
- 单独记录 arrival rate 和 random seed。
- 由于缺少真实时间戳，不能用它单独证明真实用户到达下的公平性。
- 其平均轮数明显少于 Bidaw trace，answer-length eviction 的收益可能被削弱。

### 7.3 长上下文 SSD 压力：LEval 与 LooGLE

LEval/LooGLE subset 用于对齐 Tutti 风格的长上下文和高 SSD 命中实验：

- 按 context token bucket 报告结果，而不是只给全局平均。
- 控制 GPU/DRAM/SSD 容量，形成可复现的 tier hit rate。
- 用于测 restore bandwidth、GPU bubble 和 layer/group overlap。
- 不用它们声称“还原真实多轮用户行为”，因为其到达时间是模拟的。

### 7.4 受控合成 workload

保留一组简单合成实验，用于隔离机制变量：

- 固定 prompt/context/output 长度。
- 扫描 GPU KV 容量和命中率。
- 扫描 RPS 或 users/minute。
- 扫描 read/write 比例和 SSD 副本 clean ratio。
- 构造相同总 KV bytes、不同请求大小分布，验证 disk-HRRN 是否偏置小请求。
- 构造长请求持续 aging，验证策略是否能够避免 starvation。

## 8. 固定评价指标

### 8.1 用户可见性能

- TTFT：`p50/p95/p99`。
- TPOT 或 ITL：`p50/p95/p99`。
- End-to-end latency：`p50/p95/p99`。
- Joint SLO attainment：同时满足 TTFT 和 TPOT SLO 的请求比例。
- 最大可持续 users/minute 或 RPS：在固定 SLO 达成率下的最大负载。
- 每轮对话 queueing time，以及跨 session 的公平性。

### 8.2 KV 与 I/O 指标

- GPU、DRAM、SSD 各层 KV hit rate。
- preemption、swap-out、swap-in 和 recompute 次数。
- SSD read/write blocks、bytes、requests 和有效 bandwidth。
- read/write request size distribution。
- write-read amplification：相对于必要 dirty KV 数据量的实际写入和后续重读比例。
- clean-prefix reused blocks、dirty-suffix written blocks 和 GPU-resident retained blocks。
- read queue wait、device I/O、engine observe 和 commit 延迟分解。

### 8.3 系统开销

- GPU bubble time 和 GPU utilization。
- scheduler decision overhead。
- MDS submit/poll/completion 开销。
- CPU utilization、pinned DRAM 使用量和额外 GPU metadata 开销。

不能只报告平均 TTFT/ITL。本文的调度动机直接涉及 waiting 和 starvation，因此
必须同时报告 P95/P99、最大等待时间或公平性指标，以及不同请求长度 bucket 的结果。

## 9. 实验论证路线

### 9.1 先证明问题存在

固定数据路径为 B4，在不同 GPU KV 容量和到达负载下测量：

```text
waiting queue length
preemption count
SSD write/read blocks
queueing p95/p99
TTFT p95/p99
```

目标是区分两个区域：

1. 低抢占、长 waiting 区域：后续请求因 admission 保守而产生高 TTFT。
2. 高频抢占区域：请求能够轮转，但 SSD write/read amplification 和 TPOT 增大。

### 9.2 再证明数据路径收益

对比 B1/B2/B3/B4，统一模型、KV 精度、block size、SSD cache state、context
长度和到达 trace，回答 direct I/O 消除了多少 CPU staging 与同步开销。

需要同时给出 warm/cold cache，防止 CPU page cache 或设备预热掩盖真实 SSD 行为。

### 9.3 证明双副本与 dirty write 收益

使用内部消融比较：

```text
完整 sequence write
vs.
clean-prefix reuse + dirty-suffix write
```

主要观察 SSD write blocks、write amplification、read interference 和 TTFT tail。
如果 E2E 不变，也应如实说明其原因是 read/preemption 次数未变，而不是把减写量
直接解释成用户延迟收益。

### 9.4 证明 I/O-aware scheduling 收益

至少比较 FCFS、Bidaw-style disk-HRRN 和 proposed policy：

- disk-HRRN 验证按等待时间与 KV size 联合排序的收益。
- proposed policy 进一步加入 GPU/SSD residency、dirty bytes、下一轮工作集和 read/write
  criticality。
- 对短请求、长请求分别给出 latency CDF，检查是否以牺牲长请求为代价。
- 通过 aging/starvation case 证明策略不会让大 KV 请求无限等待。

### 9.5 最后决定是否下沉调度粒度

先完成 request/block 级闭环。只有在以下证据出现后，再推进 layer-group 或
SolidAttention-style attention-inner microtask：

- SSD restore 仍占关键路径的大部分。
- request 级 prefetch 找不到足够 compute window。
- 完整 KV ready barrier 造成明显 GPU bubble。
- layer-group I/O 粒度仍能有效利用 SSD 带宽，且同步开销可控。

否则，直接重构 attention kernel 和 GPU-side DAG 会显著扩大工程面，却不一定改善
当前由 request admission 和 repeated preemption 主导的问题。

## 10. 下一阶段实现路线

### 阶段一：形成稳定 scheduler baseline

1. 固定 B4 的 FCFS 行为和配置，补齐正式 trace replay。
2. 将 scheduler decision、queue wait、block residency 和 I/O timeline 统一到 request ID。
3. 在 Bidaw trace 上找到 waiting 主导区和 preemption/I/O 主导区。

### 阶段二：实现最小 I/O-aware scheduler

1. 建立 ready queue 和 preparing queue。
2. preparing queue 先实现 disk-HRRN，作为清晰、可解释的调度基线。
3. 保留原 arrival time 和 aging，显式防止 starvation。
4. 对 restore read 设置优先级，write 只在容量水位或 slack 条件满足时推进。

### 阶段三：加入本项目的 block 工作集策略

1. 预测下一 engine step 或短窗口内会继续运行的 sequence groups。
2. pin/retain 其仍会使用的 GPU KV blocks。
3. victim selection 同时考虑 residency、dirty bytes、reload cost 和等待时间。
4. 仅对必须释放且没有有效 SSD 副本的 dirty blocks 发起 write。
5. 用 write-read amplification 和 tail latency 验证策略，而不是只看命中率。

### 阶段四：进一步重叠 I/O 与计算

1. 利用 chunked prefill 形成稳定的 engine step overlap window。
2. 评估 layer-group readiness 和 prefetch，建议先测试 4/7 层一组。
3. 当前 layer group 计算时预取下一 group，并只在 attention 使用前等待对应 group。
4. 如果 block/layer-group 调度仍不足，再考虑 attention-inner DAG 和 microtask。

## 11. 风险与边界

### 11.1 不可直接横向比较论文绝对数字

Bidaw 使用 A800、SATA RAID 和 DRAM staging，Tutti 使用 H100、企业 NVMe 和 direct
path，当前环境主要是 V100/Qwen。硬件、模型、vLLM 版本和缓存层级差异很大，
不能直接用论文绝对 latency 或 speedup 判断当前实现优劣。

### 11.2 Baseline 可复现性

CachedAttention 和 FlashGen 缺少可直接使用的完整实现；Bidaw artifact 也基于较旧
vLLM。因此论文中应优先采用当前环境可复现的 vLLM/LMCache/BaM baseline，相关
论文策略采用独立消融实现，并准确命名为 `*-style`。

### 11.3 当前多槽与细粒度边界

当前异步链路已经支持完整 reserve/commit/abort 生命周期，但多槽并发、layer-group
readiness 和 attention-inner consume 尚未构成最终闭环。它们是后续可扩展能力，
不应在当前论文叙事中描述为已实现。

### 11.4 正确性优先级

任何策略都必须保证：

- write completion 前不发布新的 SSD replica。
- read completion 前不让模型消费目标 GPU block。
- abort 能回收所有预留 block，且不破坏原 block table。
- clean/dirty 判定包含逻辑 block 位置与 token 内容，不能仅比较物理 block ID。
- session 结束、异常和取消请求不会遗留 pin 或 replica ownership。
