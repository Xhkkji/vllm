# vLLM + LMCache + BaM/GDS 调用流程记录

日期：2026-06-24

本文记录当前 `/home/xhk/llm-inference/vllm-bam` 中，vLLM V0 通过
`LMCacheConnector` 接入 LMCache，并在 LMCache storage manager 外层接入
BaM / LMCache-style GDS 的调用流程。

当前接入方式的核心结论：

- BaM/GDS 没有直接替换 vLLM attention kernel。
- BaM/GDS 没有直接替换 vLLM paged KV cache block manager。
- BaM/GDS 接在 `vLLM KVConnector -> LMCache -> storage_manager` 这条链路上。
- 在线路径中，LMCache 负责把 vLLM paged KV cache 转成 LMCache KV chunk。
- BaM/GDS wrapper 处理的是 LMCache chunk 的底层 SSD/GDS/BaM 数据面。

该函数做几件事：

1. 查当前进程内是否有 `chunk_hash -> BaM metadata`。

## 7. BaM 128KB page 数据组织

BaM page layout 定义：

- [vllm/bam/lmcache_bam_storage.py](/home/xhk/llm-inference/vllm-bam/vllm/bam/lmcache_bam_storage.py:39)

```python

```

layout 计算位置：

- [vllm/bam/lmcache_bam_storage.py](/home/xhk/llm-inference/vllm-bam/vllm/bam/lmcache_bam_storage.py:86)

```python
class LMCacheBaMPageLayout:
```

当前 Qwen2.5-7B、fp16、LMCache chunk size 256 的典型 shape：

```text
[2, 28, 256, 512]
```

含义：

- `2`：K/V 两份。
- `28`：layer 数。
- `256`：一个 LMCache chunk 的 token 槽位。
- `512`：hidden dim。
- `float16`：每元素 2B。

每个 token 向量大小：

```text
512 * 2B = 1024B
```

每个 128KB page 可放：

```text
128KB / 1024B = 128 tokens
```

每个 K 或 V 的单层：

```text
256 tokens / 128 tokens per page = 2 pages
```

一个完整 LMCache chunk：

```text
2(K/V) * 28(layer) * 2(pages per layer) = 112 pages
```

编码位置：

- [vllm/bam/lmcache_bam_storage.py](/home/xhk/llm-inference/vllm-bam/vllm/bam/lmcache_bam_storage.py:133)

```python
def encode_pages(self, tensor):
```

逻辑：

```text
[2, 28, actual_tokens, 512]
  -> pad 到 [2, 28, slot_num_tokens, 512]
  -> reshape 成 page 视图
  -> [pages_per_chunk, 131072 bytes]
```

当前满 chunk：

```text
[2, 28, 256, 512]
  -> [112, 131072 bytes]
```

尾块不足 256 tokens 时，会 pad 到固定 slot。这样每个 chunk 固定占用
`pages_per_chunk` 页，slot 到 page offset 的映射更简单：

```text
page_offset = base_row_offset + slot_id * pages_per_chunk
```

解码位置：

- [vllm/bam/lmcache_bam_storage.py](/home/xhk/llm-inference/vllm-bam/vllm/bam/lmcache_bam_storage.py:160)

```python

```

逻辑：

```text
[112, 131072 bytes]
  -> view 回 [2, 28, pages_per_kv_layer, page_token_capacity, hidden_dim]
  -> reshape 回 [2, 28, slot_num_tokens, hidden_dim]
```

## 9. SamplingMetadata 是什么

`SamplingMetadata` 是 vLLM V0 里采样阶段需要的元数据。它不存 KV，也不描述
BaM/GDS。它描述的是：模型 forward 输出的 hidden states 中，哪些位置需要拿去
计算 logits，哪些 logits 需要采样，每个 sequence group 用什么采样参数。

定义位置：

- [vllm/model_executor/sampling_metadata.py](/home/xhk/llm-inference/vllm-bam/vllm/model_executor/sampling_metadata.py:96)


它被放在 GPU model input 里：

- [vllm/worker/model_runner.py](/home/xhk/llm-inference/vllm-bam/vllm/worker/model_runner.py:146)


因此 `ModelInputForGPUWithSamplingMetadata` 包含：

```text

...
```

其中：

- `attn_metadata` 控制 attention/KV cache 怎么访问。
- `sampling_metadata` 控制 forward 输出后如何取 logits、如何采样。

`SamplingMetadata` 关键字段：

- [vllm/model_executor/sampling_metadata.py](/home/xhk/llm-inference/vllm-bam/vllm/model_executor/sampling_metadata.py:122)

字段含义：

`selected_token_indices` 是最关键的字段之一。官方注释中的使用方式：


## 10. 在线链路总览

一次真实请求的主链路可以概括为：

```text
用户请求进入 vLLM
  -> scheduler 形成 prefill batch
  -> model_runner 准备 model_input / kv_caches

模型 forward 前:
  -> need_recv_kv(...)
  -> get_kv_transfer_group().recv_kv_caches_and_hidden_states(...)
  -> LMCacheConnector.recv(...)
  -> lmcache_retrieve_kv(...)
  -> LMCache engine.storage_manager.get(key)
  -> BaM prefer-load / GDS prefer-load / 原始 LMCache
  -> 命中的 KV 被 LMCache 填回 vLLM kv_caches
  -> vLLM 可能跳过部分 prefill token

模型 forward:
  -> vLLM 正常执行 attention / MLP
  -> 新 KV 写入 vLLM paged kv_caches

模型 forward 后:
  -> need_send_kv(...)
  -> get_kv_transfer_group().send_kv_caches_and_hidden_states(...)
  -> LMCacheConnector.send(...)
  -> lmcache_store_kv(...)
  -> LMCache engine.storage_manager.put(key, memory_obj)
  -> BaM shadow write
  -> GDS shadow write
  -> 原始 LMCache SSD write

logits / sampling:
  -> compute_logits(hidden_states, sampling_metadata)
  -> logits_processor 根据 selected_token_indices 裁剪 hidden states
  -> sampler 根据 categorized_sample_indices 和 SamplingParams 采样
```

## 11. evaluation replay 与真实在线链路的区别

离线 replay 脚本：

- [evaluation/kv_chunk_trace_replay.py](/home/xhk/llm-inference/vllm-bam/evaluation/kv_chunk_trace_replay.py:1)

它不走完整 vLLM 请求调度，而是直接构造 synthetic KV chunk：

```text
shape = [2, 28, 256, 512]
```

然后直接调用：

```text
LMCacheBaMStore.store_chunk/load_chunk_tensor
LMCacheStyleGDSChunkStore.put_chunk/load_chunk_tensor
```

因此 replay 覆盖的是 chunk 数据面：

```text
同样一个 LMCache KV chunk，BaM 和 GDS 的读写带宽如何？
```

它刻意避开：

```text
tokenizer
scheduler
model forward
LMCache key 构造
prefix 匹配
vLLM paged KV cache 回填
logits / sampler
```

所以 replay 适合做 BaM/GDS chunk 层数据面 baseline，不等价于端到端 vLLM
latency/QPS 结果。

真实端到端对比仍需要跑真实 vLLM 脚本，并同时看：

- request latency
- LMCache hit/miss 行为
- `[LMCACHE_BAM_WRITE]`
- `[LMCACHE_BAM_READ]`
- `[LMCACHE_GDS_WRITE]`
- `[LMCACHE_GDS_READ]`
- `LMCACHE_BAM_VERIFY` 或 `LMCACHE_GDS_VERIFY` 的 correctness 日志

## 13. BaM 当前版 vs TARDIS/Tutti 版职责对照

这张表从调用链角度看更直观：当前 BaM 还是以 CPU 编排为主，
TARDIS/Tutti 则把更多热路径往 GPU 侧挪。

| 模块 | 当前 BaM 版 | TARDIS 风格 | Tutti 风格 |
| --- | --- | --- | --- |
| vLLM scheduler / 请求编排 | CPU | CPU | CPU |
| LMCache prefix / chunk 命中判定 | CPU | CPU | CPU |
| chunk metadata 维护 | CPU | CPU | CPU |
| page request table 生成 | CPU | CPU 协作 | 尽量 GPU |
| I/O submit / poll / completion | CPU 调 GPU primitive | GPU 主导，CPU 协作 | GPU 主导 |
| page refill / buffer 填充 | GPU kernel | GPU kernel | GPU kernel |
| cache residency / page table | CPU 管理 | CPU+GPU 协作 | GPU 优先 |
| fallback / 错误回退 | CPU | CPU | CPU |
| 日志 / 结果落盘 | CPU | CPU | CPU |

对应到 `vllm-bam` 代码层，当前最像控制面的模块是：

- `vllm/distributed/kv_transfer/kv_connector/lmcache_connector.py`
- `vllm/bam/lmcache_bam_storage.py`

当前最像热路径中间层的模块是：

- `vllm/bam/lmcache_bam_prefetch.py`
- `vllm/bam/lmcache_bam_refill.py`
- `BaM_IOStack/gids_module/bam_row_store.py`
- `BaM_IOStack/gids_module/gids_kernel.cu`

## 14. 当前代码导读

这部分是给当前已经实现的 BaM / GDS / replay 路径做一个“按代码读图”。
重点不是原生 vLLM/LMCache，而是我们自己新增的适配层和实验入口。

### 14.1 BaM 主路径

入口是：

- `vllm/distributed/kv_transfer/kv_connector/lmcache_connector.py`
- `vllm/bam/lmcache_bam_storage.py`

主流程可以理解成：

```text
LMCache memory_obj
  -> LMCacheBaMStorageManager.put/get
  -> LMCacheBaMStore
  -> BaMRowStore
  -> BaM_IOStack GPU kernel / SSD
```

写路径的数据形状是：

```text
[2, num_layers, actual_tokens, hidden_dim]
  -> pad 到 [2, num_layers, slot_tokens, hidden_dim]
  -> 切成 [pages_per_chunk, 128KB]
```

读路径的数据形状相反：

```text
[pages_per_chunk, 128KB]
  -> decode / refill
  -> [2, num_layers, actual_tokens, hidden_dim]
```

当前这条主路径里：

- `put()` 先 shadow 写入 BaM，再保留 LMCache 原始路径
- `get()` 可选先尝试 BaM prefer-load，再回退 LMCache
- `load_chunk_tensor()` 是同步 chunk 级 baseline
- `load_chunk_tensor_prefetch()` 是 page-level 中间层入口

### 14.2 page-level 中间层

入口是：

- `vllm/bam/lmcache_bam_prefetch.py`
- `vllm/bam/lmcache_bam_refill.py`

这条线把“同步读完整 chunk”拆成三步：

```text
chunk metadata
  -> page request table
  -> BaM rowctx prefetch
  -> [page_count, 128KB] pages buffer
  -> Triton refill
  -> LMCache tensor
```

其中：

- `LMCacheBaMPagePlanner` 负责把 `page_offset/page_count` 变成 `page_ids`
- `LMCacheBaMPagePrefetcher` 负责 submit / poll / get
- `LMCacheBaMPageRefiller` 负责把 `pages` 还原回 `KV tensor`

如果 Triton refill 不可用，就回退到 Python decode，保证主路径不坏。

### 14.3 LMCache-style GDS 对照路径

入口是：

- `vllm/bam/gds_baseline/lmcache_style_gds_store.py`

这条线主要是为了对照 LMCache V1 的原生 GDS 组织方式。
它的文件布局是：

```text
<gds_path>/<hash[:2]>/<hash[2:4]>/<quoted-key>.kvcache.safetensors
```

读写时的关键组织是：

- 前 4KB 作为 metadata
- payload 从 offset 4096 开始
- `use_gds=True` 时走 `cufile.CuFile`
- `use_registered_buffer=True` 时额外走 staging buffer

它和 BaM 的区别在于：

- BaM 以 page / row 为单位
- LMCache-style GDS 以 safetensors 文件布局为单位

### 14.4 replay 入口

入口是：

- `evaluation/kv_chunk_trace_replay.py`

它统一了三类实验：

```text
bam
  -> 同步 BaM chunk 读写 baseline

bam_prefetch
  -> 显式测试 page-level prefetch/refill 中间层

lmcache_gds
  -> 对照 LMCache-style GDS 数据面
```

replay 里合成的 chunk 形状固定是：

```text
[2, 28, 256, 512]
```

对这些 chunk，BaM 这边会展开成：

```text
112 x 128KB pages
```

所以 replay 的本质是：

```text
固定 shape 的 KV chunk
  -> 不同 backend 的 page / file / slab 组织
  -> 统一读写、统一校验、统一统计
```

这也是为什么它适合拿来做数据面对比，但不等价于端到端 vLLM latency。
